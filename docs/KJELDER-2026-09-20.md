## AIS: faktisk ferskheit og nødvendige atterhald

Kystverket stadfestar gratis og opne AIS-data under NLOD. Opne data omfattar norske farvatn, norsk økonomisk sone og dei nemnde sonene ved Svalbard og Jan Mayen. Fiskefartøy under 15 meter og fritidsfartøy under 45 meter er haldne utanfor. Dette inneber ikkje at alle små arbeidsbåtar er utelatne: det er bestemte fartøykategoriar som er filtrerte.

Kjelde: [Kystverket – tilgang på AIS-data](https://www.kystverket.no/sjotransport-og-havn/ais/tilgang-pa-ais-data/).

Kystdatahuset sin OpenAPI dokumenterer `/ws/api/ais/realtime/geojson`, med valfrie `aisShipType` og `timeStamp`. Utan parameter omfattar svaret fartøy som har rapportert innan dei siste ti minutta. Dokumentasjonen seier også at posisjonar vert sletta etter tjue minutt. Eldre notat om at ein kan hente tretti dagar med dette endepunktet er ikkje ein trygg garanti for produktet.

Kjelde: [Kystdatahuset OpenAPI](https://kystdatahuset.no/ws/swagger/v1/swagger.json).

**Eigen kontroll, ikkje lovnad frå leverandøren:** Eit ekte kall med `aisShipType=52` gav HTTP 200 og 136 fartøy. HTTP-dato var `2026-09-20T17:41:26Z`. Meldingsalderen var 0,73 minutt for ferskaste, median 1,15 minutt og 8,27 minutt for eldste. Dette gjeld eit avgrensa utval, ikkje statistikk for alle fartøy. Heile det ufiltrerte svaret var 2,85 MB, men eit forsøk utan komprimering fekk timeout etter 50 sekund. Det er eit konkret argument for komprimering, tidsgrenser, få førespurnader og ei tydeleg lagra reservevising.

**Tidsformat:** Det observerte feltet `date_time_utc` kjem utan `Z`, til dømes `2026-09-20T17:40:42`. Det skal tolkast som UTC. Vanleg JavaScript-parsing utan normalisering kan gje to timars feil i ein norsk nettlesar på denne datoen.

**Koordinatrekkjefølgje verifisert empirisk:** Geometrien er `LineString`, med eldst punkt først og nyast punkt sist. To fulle utvalssvar med HTTP-tid 17:41:26 og 17:45:36 UTC vart samanlikna. For fem fartøy i rørsle (VB FLOROE, SKANDI MINDER, BANAK, BUKKHOLMEN og WATERLORD) hadde det nye svaret fjerna eldre punkt frå byrjinga og lagt nye punkt til slutt. For VB FLOROE svara første koordinat i nytt svar til koordinat 11 i førre svar; den nyaste vestlege posisjonen flytta seg frå lengdegrad 3.55699 til 3.54695, i samsvar med kurs 267,6°. `date_time_utc` auka frå 17:40:16 til 17:44:17. Den eksisterande koden vel første punkt og kan dermed vise eit eldre punkt saman med nyaste tidsstempel. Rett uthenting er siste koordinat, `coordinates[coordinates.length - 1]`.

**Direkte oppdatering i nettlesar verifisert:** GET med `Origin: https://dr-grimen.github.io` til det filtrerte endepunktet returnerte HTTP 200 og `Access-Control-Allow-Origin: *`. Eit enkelt GET-kall frå GitHub Pages kan derfor lese svaret. Unngå unødvendige eigne headerar som utløyser førespurnad om førehandsgodkjenning. Bruk tidsgrense, ein førespurnad om gongen, tydeleg meldingstid og tidlegare lagra data ved feil. CORS vart kontrollert for denne GET-førespurnaden, ikkje for alle andre Kystdatahuset-endepunkt.

BarentsWatch sitt AIS-API er ein verkeleg straum og støttar siste kjende posisjonar og historikk. Det krev brukarkonto, AIS-klient og tilgangstoken med `scope=ais`. Klienthemmelegheit skal haldast på serversida eller i GitHub Secrets, aldri i den offentlege nettsida. Inga slik tilkopling er verifisert i denne kontrollen.

Kjelder: [BarentsWatch Live AIS API](https://developer.barentswatch.no/docs/AIS/live-ais-api/), [AIS-eksempel](https://developer.barentswatch.no/docs/AIS/examples/), [registrering og autentisering](https://developer.barentswatch.no/docs/appreg/).

## Mattilsynet: reelt ope API

Mattilsynet stadfestar at uthenting via REST ikkje krev autentisering. Abonnement/webhook krev Maskinporten. Den offentlege OpenAPI-spesifikasjonen vart henta komplett; versjon ved kontroll var `b5a2c39`, OAS 3.1.0. Uthentingsendepunkta krev ein `Client-Id`-header med klientnamn; dette er ikkje ei hemmelegheit eller eit kjøpt abonnement.

Kjelder: [deling av offentlege data](https://www.mattilsynet.no/om-mattilsynet/api/deling-av-offentlige-data-via-api-innen-akvakultur-omradet), [API-dokumentasjon](https://akvakultur-offentlig-api.fisk.mattilsynet.io/docs/), [maskinlesbar spesifikasjon](https://akvakultur-offentlig-api.fisk.mattilsynet.io/q/openapi).

| Endepunkt etter API-verten | Innhald og kontroll |
|---|---|
| `/api/lakselus/v2/rapporteringer` | Ekte kontroll for 2026 veke 37, `limit=2`: HTTP 200, to rapportar, `x-count: 595`. Feltene omfattar tre lusestadium, sjøtemperatur, behandlingar og resistensmistankar. |
| `/api/sykdomstilfeller/v1/rapporteringer` | Ekte kontroll med `limit=1`: HTTP 200, `x-count: 212`. Har varsling, mistanke, diagnose, avslutning, ugyldiggjering og sjukdomstype. |
| `/api/rensefisk/v1/rapporteringer` | Ekte kontroll med `limit=1`: HTTP 200, `x-count: 462`. År/månad, rapporteringstid, fôr og produksjonseiningar. |
| `/api/helsestatus/v2/lokaliteter` | Dokumentert ope endepunkt med `limit`, `offset`, lokalitetsfilter og `order-by`; innhaldet vart ikkje henta i denne runden. |
| `/api/driftsplaner/v1/aktive/soknader` | Dokumentert ope endepunkt med `limit`, `offset`, organisasjon og periodestart; dekninga vart ikkje testa på nytt. |

Tala over er observerte svartal den dagen, ikkje lovnad om nasjonal fullstendigheit. Bruk `limit`/`offset` og kontroller `x-count`; eitt kall med ei hard grense må ikkje tolkast som komplett om totalen er større. Bevar rapportveke/-år, rapporteringstidspunkt og eige hentetidspunkt kvar for seg. Rettar skal kunne erstatte eldre rapportar. Manglande data er ukjent, ikkje null lus eller frisk fisk.

Rensefiskrapportering er no ei reell kjelde: Mattilsynet publiserte tenesta 22.06.2026, med månadlege rapportar frå januar 2026. Påstandar om at alle rensefiskdata stoppar i 2018 er berre relevante for bestemte eldre BarentsWatch-datasett, ikkje for denne nye direkte kjelda.

Kjelde: [Mattilsynet offentleggjer data om rensefisk](https://www.mattilsynet.no/fisk-og-akvakultur/rensefisk/mattilsynet-publiserer-data-om-rensefisk).

## Lusegrense: viktig retting i eksisterande kode

Gjeldande rettleiing hos Mattilsynet siterer lakselusforskrifta § 8. Kravet er **færre enn** 0,5 vaksne holus i snitt per fisk, med **færre enn** 0,2 i vårvindauget:

- Nord-Trøndelag og sørover: veke 16–21, begge inkluderte.
- Nordland, Troms og Finnmark: veke 21–26, begge inkluderte.
- Elles: 0,5. Mattilsynet kan gje særskilt høgare grense for stamfisk det siste halve året i sjø.

Ved kjeldekontrollen brukte `src/events/lusegrense.ts` `>` i rå grensesamanlikning og i 0,5-greina for handheving. Dermed kunne nøyaktig 0,50 framstå som under kravet. Den tekniske råmarkeringa bør vere `>=` og kallast **«Ved/over generell grense»**. Ho er ikkje eit individuelt vedtak om lovbrot.

Kjelde: [Mattilsynet – ansvaret ulike aktørar har, med § 8](https://www.mattilsynet.no/dyr/dyrehelsepersonell/veileder-om-dyrehelsepersonell-og-bruk-av-ikke-medikamentelle-avlusingsmetoder-imm/ansvaret-ulike-aktorer-har-i-en-imm?noJS=true). Lovdata vart også forsøkt opna direkte, men svarte HTTP 405; teksten hos Mattilsynet vart brukt som offentleg primærkjelde.

Handheving ved 0,2 tek omsyn til teljeusikkerheit og fleire teljingar. Mattilsynet stadfesta 02.07.2026 at dei ikkje lenger reagerer automatisk på kvar enkelt overskriding. Appen bør difor vise tal, trend og rapportveke, med lenkje til reglane, framfor å påstå bot eller pålegg. Dette endrar ikkje sjølve lusegrensa.

Kjelder: [vårgrense og handheving](https://www.mattilsynet.no/fisk-og-akvakultur/fiskesykdommer/lakselus/lavere-lusegrense-om-varen), [oppfølging av overskridingar](https://www.mattilsynet.no/fisk-og-akvakultur/fiskesykdommer/lakselus/mattilsynets-oppfolging-av-lakselusoverskridelser).

Rapportane skal leverast seinast tysdagen i påfølgjande veke. Den pågåande veka har difor naturleg ufullstendig dekning, og skal ikkje få same status som ei eldre rapportveke. Kaldt vatn kan gje sjeldnare teljing. Kjelde: [rapportering av lakselus](https://mattilsynet.no/fisk-og-akvakultur/fiskesykdommer/lakselus/veiledning-rapportering-av-lakselus).

## Lisens, namngjeving og grenser

Mattilsynet si OpenAPI-info angjev NLOD 2.0 og retten til å avgrense/stengje tilgang ved misbruk eller overbelasting. Kystdatahuset sin spesifikasjon angjev NLOD 1.0. NLOD tillèt samanstilling og kommersiell bruk innanfor lisensen; kjelda, lisensen og eigne bearbeidingar skal opplysast. Offentlege etatar må ikkje framstå som om dei støttar produktet. Kjelde: [NLOD 2.0](https://data.norge.no/nlod/no/2.0).

**Rett BarentsWatch-vilkårsside er** [barentswatch.no/artikler/api-vilkar/](https://www.barentswatch.no/artikler/api-vilkar/). Lenka `/om/api-vilkar` i utviklardokumentasjonen gir 404. Det er derfor feil å konkludere med at vilkåra ikkje finst.

Vilkåra tillèt vidareformidling og kommersiell bruk med kreditering av BarentsWatch og dataeigaren. Påkravd synleg tekst ved bruk av API er «Data levert av BarentsWatch». Produktet må ikkje heite noko som framstår som BarentsWatch sjølv. Høg trafikk/overbelasting kan utløyse handteringskostnader; ingen generell månadspris er oppgjeven. BarentsWatch krev også at levert innhald ikkje vert endra. Bevar difor rådata og skil eigne indikatorar tydeleg frå kjeldefelta.

[BarentsWatch si opne-data-side](https://www.barentswatch.no/artikler/apnedata/) listar offisielt WFS/WMS for sjukdomslokalitetar og ILA-kontrollsoner. Ho stadfestar NLOD som hovudlisens. Metadata for kvart kartlag kan ha eigne opplysningar. Sjå datadato og gyldigheitsperiode før ei sone vert vist som aktiv.

## Tilrådd produktomfang og merking

1. Eitt kart med anlegg, fartøy og sjukdomssoner som kan slåast av/på. Søk og filter på lokalitet, selskap, fylke og produksjonsområde.
2. Anleggskort med nyaste rapportveke, dei tre lusestadia (vaksne holus, bevegelege og fastsitjande), generell grense, temperatur, behandlingar og ekte trendhistorikk.
3. Fartøykort med meldingstid, fart/kurs og kjelde. «Nær anlegg» er ei geografisk berekning, ikkje stadfesta besøk, avlusing, transport eller smitteoverføring.
4. Kjeldestatus separat per datasett: sist henta, dato/veke i dataa, og om reservekopi vert vist. Ein grønn status for éi vellukka kjelde må ikkje dekkje over feil i ei anna.
5. Sjukdomshendingar med faktisk datert status. Ei manglande sluttdato eller eit fråvær i eit anna datasett beviser ikkje at sjukdommen er aktiv eller avslutta. WFS-feltet `tomtdato` er dato for tømming og bør ikkje åleine omtalast som verifisert sjukdomsfriheit.
6. Rensefisk og driftsplanar bør få tydeleg opplyst dekning når dei vert integrerte; dei er ikkje «alt frå Mattilsynet». Tausheitsbelagde data og upubliserte individuelle vedtak vert ikkje tilgjengelege gjennom eit offentleg API.

**Ord som må brukast varsamt:** «sanntid» ved statisk dagleg oppdatering, «alle fartøy», «smittepress» for ein eigen ikkje-validert modell, «brønnbåt» basert berre på AIS-typen Fish Carrier, og «godkjend no» utan kontroll av både frå- og til-dato i transportregisteret. Bruk «oppført i Mattilsynet sitt transportregister» med datodetaljar når det er dette dataa faktisk viser. Eit positivt registertreff seier kva som er godkjent, ikkje kva oppdrag båten utfører no; eit manglande treff kan også skuldast manglande/endra kallesignal.

Kjelde for transportregister og godkjenning: [Mattilsynet – rettleiar for transportørar](https://www.mattilsynet.no/fisk-og-akvakultur/bronnbat-og-annen-transport/veileder-for-transportorer-av-akvakulturdyr).

## Oppfølgjande kontroll: trafikklys og rask AIS

Dagens kartdata i appen har same trafikklysfargar som det offisielle 2026–2027-vedtaket: PO 3 raudt; PO 1, 12 og 13 grøne; PO 2, 4–11 gule. Raudt produksjonsområde handlar om regulering av produksjonskapasitet ut frå lusepåverknad på villaks. Det er ikkje ei PD-/ILA-kontrollsone, og det tyder ikkje at kvart anlegg har overskride lusegrensa denne veka. Kjelde: [Fiskeridirektoratet, publisert 22.06.2026](https://www.fiskeridir.no/nyheter/nye-farger-i-trafikklyssystemet-er-fastsatt).

PD-/ILA-soner omfattar vernesoner, overvakingssoner og nasjonale PD-soner. Dei er forskriftsbaserte sjukdomsrelaterte område og må ha eigne teiknforklaringar. BarentsWatch skil også mellom mistanke, diagnose, tømming og avslutta sak. Kjelde: [BarentsWatch si bruksrettleiing](https://www.barentswatch.no/veiledning/fiskehelse-forklaring-og-bruksanvisning/).

Kystdatahuset `timeStamp` er ISO date-time i UTC, og fungerer som nedre grense for meldingsalder i den observerte testen. Eit kall med no minus 120 sekund og `aisShipType=52` gav 108 fartøy, 76 926 byte dekoda JSON; meldingsalder 10,5–115 sekund (median 62). Eit tilsvarande ufiltrert kall vart for stort og fekk timeout etter 20 sekund. Dei returnerte fartøya ber framleis lange LineString-spor, så kort tidsfilter fjernar fartøy, men ikkje all geometrihistorikken deira. Typefilter 52 avgrensar til den AIS-kategorien og kan ikkje merkast som full oppdatering av brønnbåtar. Andre skipstypar er int32-verdiar utan enumgrense i dokumentasjonen. Appen bør oppdatere dei kjende fartøya som faktisk er med, og halde på gamle meldingstider for resten.

Eit ekstra lett, ufiltrert kall med `timeStamp=no−20 sekund` vart fullført innan 25 sekund: 127 168 byte JSON, 69 fartøy, sju med MMSI som allereie fanst i appen. HTTP-tid 18:12:33 UTC; meldingane var frå 18:12:11,35 til 18:12:17,19. Det viser ei praktisk løysing for delvis oppdatering av kjende fartøy, utan å avgrense til feil skipstype. Ein kan ikkje omtale dette som at alle fartøy vart oppdaterte. Tidsvindauget ligg nær kjeldeforsinkinga; eit tomt svar må handterast som ingen nye meldingar, ikkje null fartøy i sjøen.
